1 · The blocking gap: records have no identity

Everything else on this list is an improvement. This one is a defect. get_trades returns type, ticker, shares, price, date, fee, market, status and notes — and no id. The model can read a trade and cannot name it afterwards. So the most ordinary correction in a portfolio app is unreachable:

User — “That 2330 buy should have been 1,035, not 1,053.”
Assistant today — reads the trade, then proposes add_trade, because that is the only write it has. The user now owns two buys instead of one corrected buy, and every downstream number — FIFO status, cost basis, unrealized P/L — is wrong.

Two fixes, in this order. Both are additive.

ChangeWhat it does
get_trades · get_dividends
amend
Add id to every row. One key per row; the model can then reference, and the confirm card can resolve, an exact record.
update_trade · delete_trade
new
Take id plus only the fields that change. Emit a proposal on the existing action channel — never touch the DB — exactly as the add tools already do.
update_dividend · delete_dividend
new
The same, for dividends.

The action payload grows an op per row — "create" | "update" | "delete" — defaulting to create, so today's {"trades": [...], "dividends": [...]} shape stays valid and the iOS confirm card keeps parsing old payloads.

2 · Six new tools

Write propose_records replaces add_trade / add_dividend

One tool that proposes any number of records of either kind in a single call. Your action shape is already {"trades": [], "dividends": []} — arrays — but add_trade only ever fills one slot. A photo of a monthly statement with eight fills therefore costs eight calls against a six-round ceiling, and gives the user eight cards to tap.

{ "trades": [ { "op": "create", "type": "buy", "ticker": "2330", "shares": 100, "price": 1035, "date": "2026-08-19", "fee": 148, "market": "TW", "notes": "" } ], "dividends": [], "summary": "3 buys and 1 sell, Aug 2026" }

Keep add_trade and add_dividend registered for one release so a model mid-conversation doesn't break, then drop them from TOOLS.

Read get_stock_info wraps services/stock_info.py

The assistant can fetch price history but not the fundamentals your own Stock detail screen renders — sector, P/E, yield, 52-week range, 月營收 with YoY, and the eight-quarter revenue and gross-margin table. So “is 2330's gross margin improving?” falls through to a web search when the answer is already in your database. The tool should read the same source the UI does, and return the same numbers.

{ "ticker": "2330", "include": ["profile","revenue","financials"] }
Read get_lots exposes the FIFO ledger

get_trades reports a lot as open or closed but never the arithmetic underneath: which lots remain, how many shares each still holds, at what cost, and how long they have been held. Every “should I sell?” question needs that ledger, and without it the model reconstructs it from raw trades and gets partial fills wrong.

Read simulate_sale 損益試算, server-side

Given a ticker, share count and price, return what the sale would realize: lots consumed FIFO, gross proceeds, the 0.1425% commission and the transaction tax at the correct rate for the instrument — 0.3% for a stock, 0.1% for an ETF — and net realized P/L. This must be computed by the same code path as the app, not by the model. A number the assistant derives itself will eventually disagree with the number on screen, and the screen is the one the user trusts.

Read get_allocation

Weights, not totals. get_portfolio_summary gives per-currency sums; concentration questions need each position's share of the market and of net worth, grouped by sector, with the top-N and the tail. This is the donut the Dashboard already draws.

Read get_followed_indices

“Am I beating the market” should mean the indices this user follows, not a hard-coded benchmark. get_performance compares against one; the assistant currently cannot discover which ones the user actually tracks, or quote them.

4 · Confirm cards for the new writes

Adds already have a card. Edits and deletes need their own, because the risk is different: an add can be deleted afterwards, an overwrite cannot be recovered from chat. Three rules.

Edit

Show before and after on one row, changed fields only, old value struck through. Never re-summarise the whole record — the user needs to see what moves, not re-read what doesn't.

Delete

Render the record in full, and name the consequence in the button — “Delete this trade”, not “Confirm”. If deleting it changes a FIFO status elsewhere, say so above the button. Destructive confirmation uses the loss colour, and this is the one card whose action is not the default focus.

Batch

Per-row include toggles, duplicates flagged against existing records, a count in the button — the Import card, reused verbatim. One tap to accept twelve rows, one tap to exclude any of them.

All four write paths keep the existing invariant, and it is worth stating plainly in the system prompt as well as the tool descriptions: the model proposes, the REST endpoint saves, and nothing is written without a tap.

Steps 1 and 2 are worth shipping alone. Until they land, the assistant is a reader that can add but not amend — and a tool that can only ever add is how a portfolio quietly fills with duplicates.
